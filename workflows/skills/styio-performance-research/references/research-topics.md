# Performance Research Topics

**Purpose:** Supply optional Styio-specific hypotheses and discriminating experiments for the performance research skill.

**Last updated:** 2026-09-08

Read the row relevant to the assignment. These are candidate questions, not a fixed campaign order or assertions of current defects. Paths in the implementation column are relative to the selected Styio checkout; confirm current code and accepted semantics before testing. Benchmark artifacts remain owned by the external checkout.

| Question | Implementation entrypoints | Useful experiment and evidence |
|----------|---------------------------|--------------------------------|
| Where does a representative program spend its time? | `src/StyioProfiler/`, `src/StyioServices/StyioCLI/`, `src/StyioNative/` | Separate startup, compiler phases, native build, and execution for a few real task shapes. Record wall/CPU time and the dominant mechanism; prioritize by end-to-end share rather than the hottest microbenchmark alone. |
| Can natural container and snapshot use trigger disproportionate copying? | `src/StyioExtern/ExternLib.cpp`, `src/StyioResourceTopology/`, `src/StyioCodeGen/CodeGenPulse.cpp` | Vary nested payload size, read frequency, history window, and mutation pattern. Count copied bytes, allocations, live ownership, and RSS. Verify independent values, lifetimes, and frame consistency before eliminating a copy. |
| Why do equivalent source forms produce different execution costs? | `src/StyioLowering/StyioIROptimizer.cpp`, `src/StyioCodeGen/`, generated LLVM IR | Pair natural composition with a semantically equivalent explicit implementation. Inspect missed inlining/vectorization and intermediate materialization. Preserve effects, numeric rules, and snapshot/commit boundaries. Track runtime, compile time, code size, and how much source rewriting users need. |
| Does inferred callable specialization scale predictably? | `src/StyioSema/TypeInfer.cpp`, `src/StyioSema/CallableSpecializationGraph.cpp`, `src/StyioCodeGen/CallableSpecializationObjectCache.cpp` | Vary accepted type instances, call-graph fanout, recursion components, and module dependencies. Count repeated visits, unique instances, generated code, and cold/warm/cache-disabled work. Underconstrained or unsupported programs are capability results, not timing samples. |
| How much recomputation follows a small edit? | `src/StyioServices/StyioIDE/SemDB.cpp`, `Syntax.cpp`, `VFS.cpp`, `Index.cpp` | Replay body edits, signature edits, undo, and broken intermediate source at increasing project sizes. Measure edit-to-result P95/P99, invalidated/reused queries, copy volume, and retained memory. Validate result freshness and cross-file correctness. |
| At what task size does concurrency pay off? | `src/StyioRuntime/ReadyQueue.hpp`, `src/StyioExtern/ExternLib.cpp`, `src/StyioRuntime/TaskWorkerCount.hpp` | Extend the external sleep/noop route with mixed task sizes, bursts, nested spawning, and slow consumers. Measure useful throughput, queue wait, P99, fairness, settlement, and memory. Investigate queue contention before choosing batching or another dispatch structure; distinguish implemented queue pressure from unimplemented stream-backpressure contracts. |
| Is long-running memory growth live state, retention, or allocator behavior? | Runtime handles/containers, resource histories, task release, and IDE/observable caches in the selected scenario | Repeat an identical lifecycle, inspect active object counts and retained bytes, and compare the post-drain state. Separate useful history, reusable capacity, fragmentation, and unreleased ownership. Report observed stability intervals without promising indefinite stability from a finite soak. |
| Do diagnostics reduce correct repair effort? | `src/StyioServices/DiagnosticContract.hpp`, parser recovery, Sema, IDE diagnostics, existing negative fixtures | Perturb valid programs with one realistic error. Measure root-location accuracy, unrelated cascades, repair rounds, and preservation of task intent. Keep diagnostic latency separate from diagnostic usefulness. Agent repair success is evidence about that agent/task setup. |
| Can users predict symbolic resource and stream behavior? | Active feature SSOTs, canonical examples, compiler/IDE feedback | Use output prediction, change requests, and explanation tasks for copy, snapshot, commit, zip, and absence behavior. Record correctness, documentation lookups, and edits needed. Agents can generate and classify cases; use human study data for conclusions about human learning or comprehension. |
| How much observability is needed to diagnose a slow program? | `src/StyioRuntime/ObservationBuffer.cpp`, `src/StyioServices/StyioObservable/`, the existing runtime observation measurement seam | Compare the accepted disabled/static/aggregate/sampled/detailed modes on the same synthetic fault. Measure CPU, allocations, P99, bytes, event loss, and diagnosis accuracy. Read numeric budgets externally and preserve disabled-path requirements; do not enable a mode by default based on an exploratory sample. |

## Primary Reference Entry Points

Use these to locate the relevant maintained source and verify current behavior. Record the exact source revision used in the study; do not present a historical blog's speedup as a measured Styio result.

- [LLVM optimization remarks](https://llvm.org/docs/Remarks.html) and [vectorizers](https://llvm.org/docs/Vectorizers.html): explain missed transformations and inspect the corresponding LLVM pass source.
- [Tokio scheduler design](https://tokio.rs/blog/2019-10-scheduler) and [runtime source](https://github.com/tokio-rs/tokio/tree/master/tokio/src/runtime): investigate queueing, work distribution, wakeups, and allocation in context.
- [rust-analyzer architecture](https://rust-analyzer.github.io/book/contributing/architecture.html) and [source](https://github.com/rust-lang/rust-analyzer/tree/master/crates): study incremental dependencies, immutable syntax, and separation of function-body and global facts.
