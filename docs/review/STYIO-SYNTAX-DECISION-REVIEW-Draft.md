# Styio 语法决策审查与讨论队列

**Purpose:** 只维护尚需语言所有者决定的语义问题、依赖关系、历史经验与推荐方案；已经批准的结论进入设计文档和决策账本，编译器实现、迁移与测试不伪装成语法问题。

**Last updated:** 2026-07-25

**Status:** Draft — unresolved language-owner decisions remain.

## 1. 审查结论

旧报告中的“253 个原子问题”不是 253 个需要讨论的语言选择。它混合了：

- 已经批准的语义；
- 从批准结论直接推导出的后果；
- 编译器、IDE、文档、测试和迁移工作；
- 尚未获准进入语言的设想；
- 真正需要所有者权衡的语义。

重新归属后，最初得到 10 个所有者问题簇。`Q01` 与 `Q02` 已于 2026-07-19 批准并移入
规范/决策账本；`Q03-F` 与作为 Q05 稳定子决策的 `Q05-LIT-ADD` 又于 2026-07-20
获批。Q05 仍有转换、其余运算符、别名/无符号、容器/矩阵与 NaN 等未决内容，因此
现在剩 **7 个活跃问题簇**。每簇选择一个完整政策，通常同时关闭十余个旧核对项；只有
所有者明确拆分某条政策时，才产生一次更小的后续讨论。未获准特性的条件性细节不进入
问题总数。

当前顺序如下：

1. `Q04-Core` 所有权、转移、捕获与能力；
2. `Q05` 剩余数值模型；
3. `Q06` Unicode、文本与解码；
4. `Q07` 乘积类型、记录与模式；
5. `Q08` 集合、迭代、范围与切片；
6. `Q09` 资源族扩展与一致性；
7. `Q10` 模块、可见性与命名空间。

`Q04-Core` 是唯一正在讨论的问题。`Q01-A` 已冻结“成功类型 + 有限名义完成族”，
`Q02-BC` / `Q02-SIG` / `Q02-INF` 已冻结显式边界合同、定义点主约束推断及
capture-safe 资格门，`Q03-F` 已冻结严格值、纯依赖图、显式 effect/completion 序列、
completion stop、发布边界和优化权限，`Q05-LIT-ADD` 已冻结精确数值字面量与封闭标量
`Add` 的 10 条合同。方向符号 `left -> right`、Unit 成功、`?|` 精确结算、无关键词的
`family(binding)`、边界调用者“结算或传播”的义务、完成上界拼写、每次调用新鲜
实例化、类型方案终身稳定、Q03-F 求值图和已批准数值关系都不会重问。现在必须把
ownership/alias/capability/drop 事实接到 Q03-F 的 `EvaluationFacts` 与 DAG，同时决定
Q02 所需的 capture-safe 证明、endpoint 的 copy/borrow/consume 模式以及 borrow/escape
边界。该核心同时解锁 Q07、Q08、Q09，并避免 Q03-F 实现长期把所有相关节点保守记为
Unknown，所以其依赖/解锁价值高于立即展开剩余数值子包。

## 2. 固定工作流

### 2.1 提问前

1. 先把该问题簇的全部子问题登记在本报告。
2. 标出已冻结前提、历史失败经验、备选政策、推荐政策和依赖。
3. 合并能由同一不变量决定的细节；实现方式不得冒充语言选择。
4. 在问题末尾列出“本次覆盖 / 转交其他问题簇 / 暂不准入”的完整表。

没有先登记的临时问题，不得在对话中突然要求所有者决定。

### 2.2 一次讨论

- 一次只激活一个最高价值问题簇。
- 默认询问一个整包政策，而不是逐个询问所有机械后果。
- 所有者可以批准整包、修改其中一条，或拒绝后要求拆分。
- 已冻结前提只作为边界展示，不包装成新问题。

### 2.3 回答之后

1. 当场把结论写入唯一的规范语义所有者。
2. 同步 EBNF、符号速查和活跃语法摘要，但不在镜像文档创造新语义。
3. 在[语言决策账本](../design/Styio-Language-Decision-Ledger.md)登记链接。
4. 为实现、迁移、负例和门禁写 Better Plan；计划不得反向修改语义。
5. 从活跃队列删除已决定问题，再激活下一个依赖已满足的问题簇。

## 3. 已冻结边界

完整内容只在[语言决策账本](../design/Styio-Language-Decision-Ledger.md)维护。
本报告只列出不应再次提问的边界：

- 普通 `T` 永不包含缺值；可缺值只能是 `? | T`。
- `(?)`、`[?]`、`{?}` 是同一个空值；嵌套 Optional 归一化。
- `unit`、`never`、缺值、失败、EOF、未初始化和 `@()` 互不等同。
- 每个绑定都有 RHS；不提供隐式零值、默认值或未初始化存储。
- `=> expr`、`=> { expr }`、`=> { <| expr }` 仅在单表达式 Block 等价。
- `<| expr` 只完成当前词法 Block；多语句 Block 没有隐式尾表达式。
- `|<| expr |;` 与 `<| expr` 同义，且 `|;` 必须存在。
- Block 候选值在必需退出义务结算后才发布；逻辑计数与物理载荷分离。
- 普通值没有 `a | b` 或 `a ?? b` 回退运算符。
- `left -> right` 只有“左侧产生的数据流到右侧位置/端点”这一种图形语义。
- `?|` 与 `->` 正交；`?| operation -> target | fallback` 不声明目标。
- 每个操作有一个成功类型和有限名义完成族集合；不存在普通 `Result` 包装或环境失败通道。
- `family` / `family(binding)` 精确匹配；两处名字均为普通标识符，不是关键词。
- 成功方向传输产生 Unit；恢复惰性且只执行一次；未处理完成族静态传播。
- catch-all 只覆盖剩余可恢复失败；absence/EOF/cancel/shutdown/fatal/pressure 保持分离。
- `?| operation | ...` 被拒绝；结算不隐式重试、调度或丢弃结果。
- 可调用边界合同写作 `T ?| {family, family}`；写出 `: T` 而无完成子句恒为空上界，
  只有合格非边界局部定义省略整个 `: T` 才可推断完整操作摘要。
- 合格的 final、非递归、非边界、捕获安全 callable value 在定义点形成唯一最一般的
  rank-1 主约束方案；每次调用新鲜实例化，不读取未来调用，也不被首次调用定型。
- `# f = ...` 不产生首用定型或弱类型变量；它只能实现既有稳定方案。公开/导出、递归、
  原生/FFI 和类型化协议边界继续要求显式合同；未解类型不进入 SGIR/LLVM。
- `Q03-F` 已冻结：普通值严格取得，独立 safe-pure 兄弟只有依赖顺序；Block 顶层项目及
  既有 data/control/resource 边排序 order-sensitive 计算，两个未排序的 order-sensitive
  兄弟静态拒绝。`source` 与 endpoint capability 是 transfer 的独立前提，箭头方向不排序
  二者；completion 跳过尚未开始的普通 Block 后继但不回滚既有外部 effect。
- Q03-F 的 `EvaluationFacts` 与 DAG 可承载 effect/access、normal-return、优化权限及
  ownership/drop 等依赖，但 Q01-A 的 `OperationSummary(success_type, completion_set)`
  保持唯一且不增加字段。
- `Q05-LIT-ADD` 已冻结：字面量延迟物化，普通具体边界晚默认 `i64`/`f64`，封闭标量
  `Add` 无 C 式混合提升，整数检查溢出并产生无 payload 的 `overflow`，浮点严格遵循
  固定 IEEE 行，常量求值与运行时一致，泛化 `Add` 方案采用有限保守完成并集。
- 上述数值子决策没有批准显式转换拼写、减乘除/除零/回绕、平台别名或无符号类型、
  string/容器/矩阵 `+`、NaN payload/equality/order；文本关系转 Q06，容器/矩阵关系还需
  Q08，其余内容仍属于活跃 Q05。

## 5. 问题簇档案

### 已关闭：Q01 — 操作完成、静态失败与 `?|` 结算

所有者于 2026-07-19 批准 `Q01-A`。完整语义只在
[Operation Completion and Settlement](../design/Styio-Operation-Completion-and-Settlement.md)
维护，决策索引见[语言决策账本](../design/Styio-Language-Decision-Ledger.md)，一次性
实现与旧路线删除已并入
[Directional Flow and Operation Settlement Plan](../plan/Styio-Directional-Flow-and-Settlement-Plan.md)。

本报告保留一个审计墓碑：`io(err)` 中 `io` 是可由 prelude/协议声明的普通
完成族标识符，`err` 是作者选择的分支局部载荷绑定；二者都不是关键词。Q01
不再接受追加子问题，公开签名如何写已由关闭的 `Q02` 接管，族声明和资源升级政策转交
`Q09`/`Q10`。

### 已关闭：Q02 — 静态类型、推断与可调用签名

**背景与用途。** 当前已有类型标注、最终/可变绑定和可调用绑定；`Q01-A` 又新增
了必须进入可调用类型的有限完成族事实。所有者已批准 `Q02-BC`：公开、递归、
原生/FFI 和类型化协议边界必须具有有限完成族上界，调用者必须静态结算或传播。
已批准的 `T ?| {family, family}` 不是完成族
定义、处理器或返回值构造，而是可调用的静态接口合同：它同时告诉定义检查器“函数
体最多允许哪些完成族越过边界”，并告诉调用者“正常取得 `T` 之外还必须结算或继续
传播哪些族”。合同语义、源码拼写、空集/推断区分、局部推断是否查看调用点、
可调用重绑定、参数省略和其他推断边界现均已由 `Q02-SIG` / `Q02-INF` 统一。

**历史经验。** OCaml 展示了强局部推断，也证明可变状态与多态结合会迫使语言
引入 value restriction/弱类型变量；Rust 把命名函数和闭包分层，闭包参数可由
上下文推断，而函数项目保留明确签名边界；Kotlin 甚至提供 explicit API mode，
避免公开 API 因推断结果变化而漂移；TypeScript 的 `any` 会直接关闭相关路径的
类型检查并继续传播；Koka 证明完成/effect 集合可以进入类型并参与推断，也展示
了行多态和全效应推断会显著扩大类型系统。Java 的 catch-or-specify 证明“可恢复
结果进入接口”能够强制调用者处理，也留下了声明负担过高时用户转向 unchecked 的
教训；Zig 则明确记录了推断 error set 会影响函数指针、跨目标稳定性并与递归冲突。
Styio v1 没必要同时承担这些复杂度，也不能重复 Java 式逐层污染和逃逸。

参考：[OCaml polymorphism limitations](https://ocaml.org/manual/4.14/polymorphism.html)、
[Rust functions](https://doc.rust-lang.org/reference/items/functions.html)、
[Rust closures](https://doc.rust-lang.org/stable/reference/expressions/closure-expr.html)、
[Kotlin explicit API guidance](https://kotlinlang.org/docs/api-guidelines-simplicity.html)、
[TypeScript `any`](https://www.typescriptlang.org/docs/handbook/declaration-files/do-s-and-don-ts.html)、
[Koka type/effect inference](https://koka-lang.github.io/koka/doc/book.html)、
[Java catch-or-specify](https://docs.oracle.com/javase/tutorial/essential/exceptions/catchOrDeclare.html)、
[Zig inferred error sets](https://ziglang.org/documentation/master/#Inferred-Error-Sets)。

**审计问题。** 本簇曾经需要决定完成上界的源码拼写、空集与推断如何无歧义区分、
可变绑定能否改变类型、局部推断能否读取调用点、参数何时可省略、可调用重绑定、
推断失败策略，以及重载/默认参数/可变参数是否准入。这些问题现已关闭；边界上界及其
“实际集合为子集”的语义也不再重问。

**批准结果。** `Q02-BC`、`Q02-SIG` 与 `Q02-INF` 均已于 2026-07-19 批准。合格定义接受
`# identity := (x) => x` 与 `# add_five := (x) => x + 5`：前者推导输入与输出
保持同型，后者保留“输入支持与精确字面量 `5` 相加”的符号约束，而不是先猜一个
具体数值类型。`Q02-INF` 采用定义点主约束类型方案；它不读取未来调用点，不允许
“第一个调用”定型，也不引入 `any`/`dynamic`。泛化位置、可变绑定/捕获/递归边界，
以及 Q02 与 Q05/F02 的分工已经冻结；完整审计保留在第 10 节，不再向所有者提问。

### 已关闭：Q03-F — 严格性、依赖求值、effect/completion 序列与提交时机

所有者于 2026-07-20 批准 `Q03-F`。普通值严格取得，独立 safe-pure 兄弟只有依赖
顺序；Block 项目和既有 data/control/resource 边提供显式 effect/completion 序列，
未排序的 order-sensitive 兄弟失败关闭。`source` 与 endpoint capability 是 transfer
的独立前提，completion stop、惰性选择、发布屏障和四类优化权限也已冻结。

唯一语义所有者是
[Functional Evaluation and Effect Ordering](../design/Styio-Functional-Evaluation-and-Effect-Ordering.md)，
实现、迁移、负例和删除由
[Functional Evaluation and Effect Ordering Plan](../plan/Styio-Functional-Evaluation-and-Effect-Ordering-Plan.md)
拥有。第 12 节只保留批准与转交审计，不再构成待批准的平行语义说明，也不再接受
“全部左到右”、effect 顺序 unspecified、隐式事务或全面 lazy 等旧方案。

### 当前：Q04-Core — 所有权、转移、捕获与能力

**背景与用途。** `Q03-F` 已经决定一个 computation 何时能运行、何时停止和何时发布，
却故意不决定 value copy、owner move、borrow/view、capture、endpoint consumption 或
drop。Q03-F 的 `EvaluationFacts` 和 DAG 需要 ownership/alias/capability/drop 事实，
`Q02-INF` 又只消费一个已证明的 capture-safe 结果；若 Q04 继续空缺，前端只能把相关
节点保守记为 Unknown，Q07/Q08/Q09 也无法在稳定基础上定义部分移动、视图和资源协议。

**已经冻结但不等于全局模型。** 资源 session 已冻结 handles/anchors-only、session owner
不逃逸、owned task 在退出前 join、默认 reverse-order Close；Block 发布已冻结
last-borrow、child-join、commit、drop 等真实依赖优先于稳定逆登记顺序。它们是局部
锚点，不等于“所有普通值、容器、闭包、task 和 endpoint 的全局所有权模型已经批准”。
现有目标文档里关于 move-only resource 或 capability 表的建议必须在本包中明确归类，
不能靠实现或一句 “accepted baseline” 偷渡为通用规则。

**必须决定。** 与物理对象大小无关的 value/owner/borrow 分类、聚合传播、bind/rebind
和 consume 的所有权提交点、完成后的静态 post-state、closure/task capture mode 与
escape、endpoint 的 copy/borrow/consume 合同、last-borrow/drop/join 边，以及这些事实
怎样接入 Q03-F 而不改写 Q01-A 的 `OperationSummary`。完整当前讨论包见第 13 节。

**推荐。** 采用“值语义 + 仿射 owner + 词法 borrow + 协议化 endpoint”：一个类型是否
具有 value semantics 由身份与可观察行为决定，绝不由对象是否 “small” 决定；实现可在
不可观察身份时使用 memcpy、COW 或共享表示。owner 默认不可隐式复制，borrow/view 不
逃逸；capture mode 由类型、使用与 escape 事实唯一推导，否则失败关闭；endpoint 协议
而非 `->` 字形声明 copy/borrow/consume。Q04 只产生独立 ownership facts 和 DAG 边，
不扩充 `OperationSummary(success_type, completion_set)`。

### Q05 — 数值模型

**背景与用途。** 整数/浮点字面量、别名、溢出、除零、转换和矩阵标量运算若各自
推断，会产生平台差异和隐藏数据损失。

**历史经验。** C 的有符号溢出未定义行为会破坏直觉；Java 的固定回绕可预测但
可能静默损坏；Rust 把 debug/release 溢出行为和 `as` 转换分开，仍容易产生模式
差异；Swift 默认陷阱并另设回绕运算符；IEEE 754 的 NaN 破坏全序和普通相等。

**已批准子决策。** 所有者于 2026-07-20 批准 `Q05-LIT-ADD`：精确字面量、晚默认、
封闭标量 `Add`、无混合具体类型提升、检查整数溢出、固定 IEEE 浮点行、编译/运行一致、
泛化完成并集与常量已知溢出合同均已冻结。完整 10 条和历史依据保留在第 11 节。

**仍必须决定。** 显式转换表面及窄化/饱和政策、减乘除/除零/余数/幂/回绕、数值别名
与无符号类型是否准入、NaN payload/equality/order，以及这些关系与后续集合/文本设计
的边界。Q03-F 已满足标量 relation 所需的求值/停止/发布依赖；文本 `+` 转 Q06，容器/
矩阵关系仍待 Q08 的集合语义后由 Q05 + Q08 共同准入。Q05 没有关闭，当前后端也不得
填补这些空白。

**剩余推荐基线。** 转换必须显式且失败模式可见；每个其余运算符分别给出有限操作数、
结果与 completion 关系，不从 `Add` 机械复制；回绕/饱和需独立准入；编译期与运行期
继续一致；不要预设 `cast[T]` 或其他未批准拼写。

### Q06 — Unicode、文本与解码

**背景与用途。** 源码标识符、`char`、字符串索引、切片、长度、文件/终端解码
若使用不同单位，会产生安全漏洞和边界错误。

**历史经验。** Java/JavaScript 的 UTF-16 code unit 让代理项泄漏到用户算法；
Python 的 code point 仍不等于用户感知字符；Swift 的字素正确但随机索引成本高；
Unicode 同形字符和双向控制符已经造成源码供应链风险；自动替换非法字节会丢失
取证信息。

**必须决定。** 源文件编码、标识符归一化和混写限制、`char` 单位、字符串长度/
索引单位、字节视图、非法序列、解码失败、规范等价。

**推荐。** 源码与字符串存储 UTF-8；标识符采用统一归一化并拒绝危险双向控制/
混写；`char` 是 Unicode scalar，不是假装成字素；字节、标量、字素 API 分层；
默认字符串不承诺 O(1) 随机索引；解码失败进入已冻结 `Q01-A` 的名义完成族而非静默替换。

### Q07 — 乘积类型、记录与模式

**背景与用途。** 元组、记录、解构、match、相等/哈希和 FFI 布局需要一致的身份
与穷尽规则。

**历史经验。** TypeScript 的全面结构类型容易把偶然同形当成同一协议；Rust 的
名义结构体和穷尽 match 很安全，但部分移动与借用模式复杂；Scala 的 extractor
把任意代码藏进模式；C ABI 的 padding 说明源码结构不能自动等于外部布局。

**必须决定。** 元组/记录身份、字段顺序、结构相等、模式穷尽、guard 覆盖、
重复/缺失字段、部分移动、ABI 布局。

**推荐。** 元组按位置结构化；命名记录按声明名义化并保留声明字段顺序；模式是
纯匹配而非任意 extractor；封闭值域必须穷尽；guard 不计作静态穷尽证明；ABI
只能通过显式外部适配器。

### Q08 — 集合、迭代、范围与切片

**背景与用途。** list/dict、迭代、range、slice、stride、series 窗口和文本解码
共享端点、顺序、视图/物化和越界问题，却不应被一套标点强行同义化。

**历史经验。** Python 的半开切片组合良好，但负步长规则不直观；Go 的 map 顺序
故意不稳定，不能用于可复现语言语义；JavaScript 对键的字符串化和对象顺序留下
兼容包袱；C++ iterator 失效规则细碎；惰性视图若借用临时容器会悬垂。

**必须决定。** dict 顺序/键、range 包含性和下降、slice 端点/负索引、stride、
越界、视图还是副本、迭代失效、series 暖机与历史上限、EOF 驱动。

**推荐。** dict 保证插入顺序；range 与 slice 分别定义，不靠“看起来相同”推导；
切片采用半开边界；下降必须显式表达；容器 mutation 使迭代器失效并静态/动态
拒绝；默认切片物化，只有显式视图才借用；series 状态受声明上限约束。

### Q09 — 资源族扩展与一致性

**背景与用途。** 资源成员、压力、关闭、能力和用户扩展若没有唯一归属，两个模块
可能为同一类型定义互相冲突的行为。

**历史经验。** Ruby monkey patch 和开放类让行为随导入顺序变化；C++ ADL/ODR
使扩展查找与链接冲突难诊断；Rust orphan/coherence 规则牺牲部分自由换取唯一
实现；Swift extension 方便，但跨模块同名成员仍需清晰解析规则。

**必须决定。** 用户资源族是否准入、谁可定义成员/协议实现、覆盖/最终、命名空间、
捕获、压力族激活和冲突诊断。

**推荐。** v1 只开放 prelude/编译器登记资源族；先冻结能力与 coherence 规则，
再用独立准入门决定用户扩展；任何候选实现必须全程序唯一且与导入顺序无关；
压力观察协议已设计，但具体资源族激活是产品/实现工作，不是新语法问题。

### Q10 — 模块、可见性与命名空间

**背景与用途。** 规范模块身份和导入拼写已有基础，但默认可见性、导出、重导出、
别名、选择导入、循环与初始化顺序仍需统一。

**历史经验。** JavaScript barrel re-export 容易制造循环和不稳定初始化；C/C++
头文件/ODR 把同一身份交给构建系统；Rust glob import 会增加歧义但模块身份明确；
Go 默认导出简单，却把大小写变成 API 语义。

**必须决定。** 默认私有/公开、显式导出、重导出、别名/选择导入、歧义、循环、
模块初始化、资源族命名空间。

**推荐。** 默认私有且显式导出；规范路径决定唯一身份；别名不创造第二身份；
循环依赖和循环初始化失败关闭；v1 暂不准入 glob、重导出和选择导入，分别保留
一个未来准入门。

## 10. 已关闭讨论包审计：Q02

### 10.1 不再讨论的前提

- 普通绑定必须有 RHS；`=` 允许换值，不代表允许换类型。
- `Q01-A` 已确定每个操作具有 `OperationSummary(S, completion_set)`；本次只决定
  这些事实何时推断、何时显式，以及公开签名怎样写。
- `Q02-BC` 已确定公开、递归、原生/FFI 和类型化协议边界必须声明有限完成族上界；
  实现实际集合只能是其子集，调用者必须结算或继续传播。该语义不再与拼写捆绑重问。
- `Q02-SIG` 已确定非空上界写作 `T ?| {family, family}`；`: T` 无子句恒为空，
  只有合格的局部定义省略整个 `: T` 才能推断完整操作摘要。
- 当前可调用返回类型写在名字后：`# add : i32 := (a: i32) => ...`。
- `family`、`io`、`timeout` 等完成族名字仍是普通标识符，不得变成关键词。
- 编译器内部类型变量、定义点 rank-1 泛化与使用点实例化属于 `Q02`，不要求作者
  书写新语法。作者可写泛型/约束、用户能力或运算符实例、公开泛型合同、高阶/高秩
  多态及完成行变量属于 `F02`；捕获/借用属于 `Q04`；整数/浮点字面量、内建运算符
  的操作数—结果—溢出—完成族关系属于 `Q05`；具体 export 表面属于 `Q10`。

### 10.2 已批准签名到底声明什么

以下是已经批准的规范表面：

```styio
# read_price : f64 ?| {io, parse} := (path: string) => { ... }
```

| 片段 | 声明的事实 | 不会定义或触发的东西 |
|---|---|---|
| `# read_price` | 现有规则下名为 `read_price` 的可调用绑定 | 不定义完成族 |
| `(path: string)` | 输入槽位及其类型 | 不从未来调用点反推参数类型 |
| `f64` | 正常完成时产生的值类型 | 不是默认值，也不包含缺值 |
| `?| {io, parse}` | 允许越过该可调用边界的名义完成族上界 `{io, parse}` | 不是 `Option`、普通 union、fallback、处理器、运行时 set/dict 或 `Result` |
| `{ ... }` | 实现体 | 不得产生签名上界之外的完成族 |

`io` 和 `parse` 必须已经由别处的完成族声明引入；本行只引用它们。它也不声明族
载荷：`io(problem)` 中 `problem` 的类型来自 `io` 自己的声明。完成族声明表面、
命名空间和可见性仍分别归 `Q09`/`Q10`，这里不偷定。

**定义之后，编译器怎样使用。** 编译器从函数体求实际摘要并对照合同：

- `OperationSummary(f64, {io})` 满足上界，定义通过；
- `OperationSummary(f64, {io, timeout})` 越过上界，定义处报错；
- `OperationSummary(string, {io})` 的正常结果类型错误，定义处报错；
- 函数体以后不再产生 `parse`，仍可保留原上界，调用者接口不会被实现细节静默改变。

**调用者怎样使用。** 调用得到的不是可供用户拆箱的 `Result` 值；它仍是一次操作：
正常路径产生 `f64`，未正常完成时沿静态控制边离开。调用者可以完整结算：

```styio
price : f64 =
    ?| read_price(path)
     | io(problem) => price_from_cache(problem)
     | parse(problem) => 0.0
```

两个恢复表达式的正常结果都必须能汇合为 `f64`。调用者也可以只结算一部分：

```styio
# load_price : f64 ?| {parse} := (path: string) => {
    ?| read_price(path)
     | io(problem) => price_from_cache(problem)
}
```

这里 `io` 被本地结算，未匹配的 `parse` 静态传播到 `load_price`，所以外层合同必须
允许 `parse`。恢复表达式自己产生的新完成族也按 `Q01-A` 继续传播；没有动态栈搜索、
隐式重试或程序级错误通道。

**采用这种合同会产生的后果。**

1. 调用者即使看不到函数体，也能从签名知道必须结算或传播什么；递归、原生和分离
   编译边界不需要对整个调用图求固定点。
2. 增加一个公开完成族是接口破坏性变化；删除实现中的某个完成族不是破坏性变化，
   除非作者同时主动收窄公开上界。
3. 私有局部定义可以推断以减少重复，但公开链条若逐层原样暴露 `io`，会重演 Java
   checked exception 的低层细节污染和 catch-or-specify 样板。设计必须要求在合适的
   抽象边界结算或映射成领域完成族，不能靠宽泛顶层族逃逸。
4. 高阶函数若要透明转发任意回调的完成集合，最终需要 `F02` 的完成行多态；v1
   显式高阶边界只能接受一个已知上界，不能假装已经解决通用包装器问题。
5. 完成上界属于静态可调用类型和接口兼容性，但不要求堆对象、异常展开、隐藏
   `Result`、动态表或运行时类型搜索。
6. 已批准拼写复用 `?|`，但以 `{...}` 和逗号把签名中的静态族集与表达式结算分支
   明确分开，不恢复裸二元 `|`。
7. 空集/推断已经词法化：只要作者写出 `: T`，省略完成子句就永远表示空上界；
   只有连 `: T` 都省略的合格局部定义才能推断整个正常类型和完成集合。

因此，这一行真正要解决的问题不是“怎样写失败”，而是：**可调用的正常结果之外，
哪些可恢复完成允许越过接口边界，并由谁承担结算责任。**

### 10.3 方案 A — 定义点主约束方案 + 显式边界签名（推荐）

所有者已经否决“没有唯一具体类型就失败”的前提，并明确要求以下两行是有意义的
定义，而不是等待某次调用把参数定型：

```styio
# identity := (x) => x
# add_five := (x) => x + 5
```

第一行表达“怎样进来就怎样出去”；第二行表达“任何能够以 Styio 已定义语义与精确
整数字面量 `5` 相加的输入”。编译器必须保存类型变量之间的关系和行为约束。为避免
与 Styio 源码中的方向符号混淆，本文只用以下**编译器元记法**描述结果；`forall`、
`Fn`、`Add` 和 `Literal` 都不是拟议源码关键词、trait 或新语法：

```text
identity : forall A. Fn(param=A, result=A, completions={})
add_five : forall A, R. Fn(param=A, result=R,
                           requires={Add(A, Literal(5), R)},
                           completions=finite-set)
```

推荐方案 A 把“尽力推导”收紧为可实现、可复现的合同：

1. **稳定的是类型方案。** 普通绑定一旦得到规范具体类型便一生同型；合格可调用
   一旦得到规范类型方案，后续每次使用可以独立实例化其中的量化变量，但绑定自身的
   参数关系、结果关系、约束和完成上界不得漂移。多实例不是可变绑定改类型。
2. **定义点产生约束。** 未标注参数/结果先成为新类型变量；名称流、返回流、字面量、
   内建运算和完成事实分别产生相等、可表示性、运算关系与完成集合约束。编译器在
   定义处统一、化简并规范化它们，而不是先选择 `i64`、`f64` 或后端默认类型。
3. **主方案是通过标准。** 若能得到唯一的最一般、可实例化且无歧义的规范约束方案，
   定义通过；若不存在方案、存在互不包含的候选、约束变量无法由参数/结果决定，或
   约束系统不能证明一致性，则在定义处要求作者补参数、结果或未来已准入的约束标注。
   “尽力”不允许启发式猜测、搜索超时后任选、静默默认或依赖优化器结果。
4. **每次调用新鲜实例化。** `identity(1)` 与 `identity("s")` 分别实例化同一方案，
   前一次调用不会永久改写参数类型。具体实参不能满足约束时，在该调用点报出缺少的
   行为或不可表示的字面量；定义体不退化成 C++ template 式任意晚期重查。
5. **推荐的泛化位置。** 只对 final `:=`、非递归、非边界、可证明捕获安全的可调用
   定义做 rank-1 泛化，并且只量化未自由出现在词法环境中的变量。建议同时覆盖词法
   局部和模块私有定义。`# f = ...` 若没有已经存在的期望方案则不自动泛化，也不留下
   会被第一次使用定型的弱变量；捕获与逃逸的进一步限制归 `Q04`。
6. **强制显式边界不变。** `Q02-BC` 已批准公开/导出、递归、原生/FFI 和类型化协议
   边界必须写正常结果、参数和有限完成上界。公开泛型合同需要未来 `F02` 的作者可写
   量化/约束语法；不得把内部推断方案偷偷发布成看不见的公共 ABI。
7. **完成上界规则不变。** `Q02-SIG` 的 `T ?| {family, family}` 仍是有限上界，定义
   实际完成集合必须是其子集。若不同内建 `+` 实例具有不同溢出/完成事实，`Q05`
   必须给出一个有限保守上界或拒绝无法形成单一有限方案的泛化；不借机引入开放完成行。
8. **可调用重绑定。** `# f = new_body` 只能替换为满足既有参数、结果、约束和完成
   上界方案的实现；实际完成集合可以更小，但外部合同不变。改变方案必须使用另一个名字。
9. **失败关闭。** 没有 `any`、`dynamic`、隐式顶类型、未知占位签名或“先编译再说”。
   递归无合同、边界缺合同、无主方案、实例约束不成立、完成族越界都由 Sema 报错。
10. **调用形状与扩展边界。** 本包不准入用户名字重载、默认参数、可变参数、用户
    `Add` 实例或结构 duck typing。Q02 只保存编译器已知的封闭内建关系；作者可写
    泛型/约束、用户能力/运算符实例、高阶/高秩多态和完成行变量仍分别走 `F02` 准入。
11. **确定性与增量编译。** 方案只依赖定义、词法环境、已声明内建关系和立即期望
    合同；不依赖未来调用点、文件顺序、哈希顺序或下游模块。规范方案和每次实例化键
    都可稳定缓存。
12. **接口事实。** 编译器/IDE 展示同一规范方案、约束来源、参数/结果关系和完成
    上界；`forall`/`Add` 等内部展示必须标为推断事实，不能伪装成作者写过的源码。

### 10.4 方案 B — 所有完成集合都推断并写入生成接口

源码最短：甚至公开/递归函数也不写完成集合，编译器对调用图求最小固定点并把
结果写入接口元数据。问题是内部新增一次 I/O 会静默改变所有上游公开签名；递归
SCC、增量编译、错误定位和跨模块缓存都变成全局问题。生成接口还会成为“真正的
API”，源码评审却看不到变化。它适合研究型全 effect inference，不适合当前仓库，
因此不推荐。

### 10.5 方案 C — 所有地方全部显式

每个局部值、闭包参数、返回和完成集合都必须写出。编译器最简单，诊断也局部，
但会否定 Styio “局部可省略、需要边界时写清楚”的渐进性能/表达理念，并让短小
pulse closure 充满重复标注。安全收益主要发生在边界而非每个局部，因此不推荐。

### 10.7 已关闭子决策：Q02-SIG

`Q02-BC` 与方案 B 已于 2026-07-19 批准。本节保留淘汰方案作为审计证据，不再
向所有者提问。

**方案 A — 裸竖线行。**

```styio
# read_price : f64 ?| io | parse := (path: string) => { ... }
```

最短，但重新出现了容易被读作 union/fallback 的裸 `io | parse`，也没有从表面解决
空集与推断的区别，不推荐。

**方案 B — 有界族集（推荐）。**

```styio
# read_price : f64 ?| {io, parse} := (path: string) => { ... }
# abs : i64 := (x: i64) => { ... }
# local := (x) => { ... }
```

- `?|` 只启动完成上界子句；`{...}` 是编译期有限名义族集，不是运行时 set/dict。
- 族用逗号分隔，不恢复普通二元 `|`；重复族、非族标识符和无穷/开放集合报错。
- 任何作用域只要写出 `: T`，没有完成子句就恒表示空上界，因此 `abs` 明确为纯。
- 只有省略整个 `: T` 的非边界局部定义才允许推断完整
  `OperationSummary(success_type, completion_set)`；不允许“结果显式、完成偷偷推断”。
- 公开、递归、原生/FFI 和类型化协议边界必须写 `: T`，所以它们永远不会依赖
  调用点或上下文猜测合同。

该方案不新增关键词或 token；代价是 `{...}` 在签名位置承担静态族集角色，必须由
格式化器固定为逗号列表，文档明确它不是未来 `set` 值语法。

**方案 C — 新关键词子句。** 例如 `completes(io, parse)` 或 `throws ...`。阅读直白，
但增加关键词并把 Styio 拉回异常术语；不推荐。

**批准结果：** 完成上界写作 `T ?| {io, parse}`；`: T` 无子句恒表示空上界；
只有合格的非边界局部定义省略整个 `: T` 才允许推断完整操作摘要。`?| {}`、重复族、
非族名字和尾逗号失败关闭。

### 10.8 已批准子决策：Q02-INF

`Q02-SIG` 已经允许合格的非边界定义省略整个 `: T`。所有者随后明确纠正：

```styio
# identity := (x) => x
# add_five := (x) => x + 5
```

两者都必须是合法且可复用的定义。`identity` 是“输入类型与输出类型相同”的桥接型
函数；它可用于适配器、组合节点、测试探针或保持类型的中间层，即使日常使用频率不高，
也没有理由被类型系统判为非法。`add_five` 则证明推断器不能只做相等统一：它必须记录
“参数支持该运算、字面量可在相应位置表示、结果由运算关系决定”的行为约束。

#### 历史失败经验怎样约束 Styio

1. Rust 闭包会从使用处得到一个具体参数/结果类型，并在首次具体调用后锁定；同一
   `|x| x` 随后不能再接收另一类型。这正是 Styio 必须删除的首用定型模型，而不是
   可借鉴目标。见 [Rust closure type inference](https://doc.rust-lang.org/book/ch13-01-closures.html#inferring-and-annotating-closure-types)。
2. Haskell 的正面经验是为 `double x = x + x` 推导带 `Num` 约束的 principal type，
   不急于选择 `Int`；负面经验是开放重载会产生歧义，并发展出数值 defaulting 和复杂
   规则。Styio 应借鉴“保存主约束方案”，拒绝静默 defaulting。
   见 [Haskell principal types](https://www.haskell.org/onlinereport/haskell2010/haskellch4.html#x10-650004.1.4)、
   [numeric literals](https://www.haskell.org/onlinereport/basic.html#sect6.4.1) 与
   [ambiguous types/defaulting](https://www.haskell.org/onlinereport/haskell2010/haskellch4.html#x10-760004.3.4)。
3. OCaml 证明把可变状态与自由泛化组合会不健全，因此引入 value restriction 和弱
   类型变量；弱变量又可能被第一次使用固定，并在之后正确用法处报出迷惑错误。
   Styio 应只泛化安全 final callable value，不把 `# f =` 或隐藏可变捕获当普通纯值。
   见 [OCaml value restriction](https://ocaml.org/manual/4.14/polymorphism.html#s%3Avaluerestriction)。
4. GHC 的歧义检查说明“约束存在”仍不等于“方案可用”：若约束变量无法从参数/结果
   或一致关系确定，调用永远无法解出它。Styio 应在定义处拒绝这种不可实例化方案，
   而不是把错误无限推迟。见 [GHC ambiguity check](https://ghc.gitlab.haskell.org/ghc/doc/users_guide/exts/ambiguous_types.html)。

#### 仓库现状与必须一次迁移的旧路径

- Parser/AST 已能承载两种源码，无需新增 token、关键字、产生式或 AST 语法节点。
- 当前 Sema 没有类型变量、约束方案或逐调用实例化；未标注参数会被第一次调用的
  实参类型永久写回共享 `ParamAST`，返回类型也只有按函数保存的单一具体缓存。
- lowering/IR 当前每个源定义只生成一个具体函数，未标注参数/结果甚至可能落成
  `i64` 默认。这不能作为新语义的兼容路线。
- 实现必须一次删除“首用改写 AST + 单值返回缓存 + 未解类型默认 i64”的旧权威，
  由 Sema 内部 type term、约束、规范方案、调用实例表和求解后单态化取代；SGIR 继续
  只接收已解具体类型。不得长期保留两套推断器。

#### 方案比较

**方案 A — 定义点主约束方案，使用点独立实例化（推荐）。** 定义体生成类型变量与
封闭约束，求出唯一最一般的 rank-1 方案；每次调用用新鲜变量实例化，随后求得具体
类型并生成/复用稳定的具体代码实例。`identity(1)` 不影响 `identity("x")`。

**方案 B — 第一次调用定型。** 实现便宜，但结果依赖调用顺序、增量编译范围与下游
代码，第二个正确调用可能因第一个调用而失败；仓库当前恰好处于这个错误状态。拒绝。

**方案 C — 扫描所有调用点后反推。** 能通过部分例子，但公共/递归/分离编译会要求
调用图固定点，新增一个下游调用即可改变上游签名，缓存和诊断都不稳定。拒绝。

**方案 D — C++ template 式每个实例重新检查任意函数体。** 表面最灵活，却把错误
推到远离定义的调用链，并造成重复求解与难以控制的代码膨胀。Styio 应在定义处证明
一个符号方案，只在调用点验证具体约束和生成已证明实例。拒绝。

#### 已由所有者确定，不再询问

1. `# identity := (x) => x` 可表达并推导同型桥接方案。
2. `# add_five := (x) => x + 5` 不预设 `x` 的具体类型；定义保留 `+ 5` 行为约束。
3. 能得到可用方案就通过；得不到则要求作者显式补充类型，而不是注入默认值。
4. 以上能力不新增源码关键词；编译器内部 `forall`、`Add` 等只是元数据/诊断记法。

#### 批准结果（2026-07-19）

所有者批准方案 A，以下条款同时冻结：

1. “能推”严格定义为存在唯一、最一般、规范化、无歧义且可实例化的约束方案；不采用
   启发式、时间预算猜测、静默数值默认、未来调用点或首用定型。
2. final `:=`、非递归、非边界、捕获安全的 callable value 才能自动 rank-1 泛化；
   同时覆盖词法局部与模块私有定义，并且只泛化不自由出现于词法环境的类型变量。
3. `# f = ...` 若没有既有期望方案便不自动泛化，也不保留弱变量；重绑定只能实现既有
   稳定方案。公开/导出、递归、原生/FFI、类型化协议边界继续要求显式合同。
4. 每次调用独立实例化；具体实参不满足约束时在调用处报错，定义歧义则在定义处报错。
5. Q02 只允许编译器封闭内建关系参与约束；Q05 决定 `Literal(5)`、内建 `Add` 的
   操作数/结果/转换/溢出/有限完成族关系。用户自定义实例、作者可写泛型/约束、公开
   泛型合同、高阶/高秩多态和完成行变量继续留给 `F02`。
6. 实现以规范具体类型向量去重单态化，使用稳定实例键/改名并设置递归实例增长与代码
   膨胀门禁；没有运行时泛型字典，也不把未解类型变量送入 SGIR/LLVM。
7. 普通具体绑定和可调用类型方案都一生稳定；`any`、`dynamic`、后端默认类型、用户
   重载、默认参数和 variadic 不由本包准入。

| 递归泛型怎样书写 | 转 `F02` | 递归仍要求显式合同；不做隐式多态递归 |
| 公开泛型 `identity` 怎样书写 | 转 `F02` + `Q10` | 需要作者可见合同及导出表面；不发布隐藏方案 |
| 用户能否声明 `Add` 或其他能力实例 | 转 `F02` | 当前不准入；未来必须先解决 coherence |
| 高阶/高秩多态与任意回调完成行 | 转 `F02` | 当前不准入 |
| 用户重载、默认参数、variadic | 暂不准入 | 各自有真实用例后分别建立准入门 |
| 实例缓存、稳定改名、代码膨胀限制 | 实现计划 | 进入独立 Q02 类型推断 Better Plan，不反向改语义 |

**关闭记录。** 所有者于 2026-07-19 批准上述方案 A 整包，关闭了“哪些定义可泛化、
怎样判定能推、每次调用怎样实例化、哪些问题必须留给 Q04/Q05/F02”这一组相互绑定的
边界。Q02-BC、Q02-SIG 与 Q02-INF 均已关闭；实现工作进入独立计划，Q02 从 active
队列移除。本节完整保留问题、淘汰路线和转交关系作为审计证据，不再向所有者提问。

## 11. 已批准子决策审计：Q05-LIT-ADD — 精确字面量与封闭内建 `Add` 关系

### 11.1 为什么它曾是最高价值阻塞项

`Q02-INF` 已经批准下面的定义合法：

```styio
# add_five := (x) => x + 5
```

但 Q02 刻意没有猜测 `5` 是 `i32`、`i64` 还是 `f64`，也没有让当前后端的一个
具体实现替语言作决定。它只留下编译器内部关系：

```text
Add(A, IntegerLiteral(5), R, C_add)
```

批准前若不给出一个有限关系，Sema 就无法判断哪些具体调用满足该方案、结果类型 `R`
是什么、完成集合 `C_add` 是什么，也无法为单态化建立稳定实例键。因此这个子决策不是
为了增加一个新运算符，而是补完已经批准的主约束推断合同。

它之所以可以先于 Q03-F 单独批准，是因为只决定静态操作数—结果—完成关系，不决定两个
操作数之间是否存在时间边、completion 后是否继续或常量折叠能否重排；那些现已由
关闭的 Q03-F 冻结，并由其唯一专题设计拥有。
`IntegerLiteral`、
`DecimalLiteral`、`Add`、关系参数和求解过程都是编译器元数据，不是源码关键词、trait、
函数名或新语法。作者继续只写普通字面量与 `+`。

### 11.2 背景、用途与必须维持的不变量

“精确字面量”指词法值在选择存储类型以前保留其数学值：整数保存任意精度的有符号
整数，十进制保存精确的十进制系数与指数。它不是承诺运行时任意精度数值，也不是一种
作者可写的隐藏类型。只有上下文或最后的默认政策选择 `i8`–`i128`、`f32` 或 `f64`
以后，才检查范围、规定浮点舍入并生成具体值。

这层分离同时服务五件事：

1. `add_five` 在定义点保持可复用方案，不因编译器偏好的整数宽度过早坍缩；
2. `x: i8 = 300` 一类错误在字面量物化点报告，而不是先截断再运行；
3. `i32 + i64` 是否允许、结果是什么不再由后端隐式转换决定；
4. 整数溢出完成与浮点 IEEE 结果能进入同一份有限内建关系；
5. 常量折叠、运行时计算、IDE hover 和单态化缓存可以共享同一规范答案。

它会直接决定下面这些源码的含义与后果：

```styio
small : i8 = 5                     // 精确整数 5 在 i8 上下文物化
count := 5                         // 若批准方案 A，普通存储边界晚默认为 i64

# add_five := (x) => x + 5         // 定义处保留约束，不默认 x

# add_i64 : i64 ?| {overflow} := (a: i64, b: i64) => a + b
safe : i64 = ?| add_i64(left, right)
             | overflow => 0
```

`count := 5` 的“默认”只是为作者已经写出的 RHS 选择一个具体类型；它绝不合成值，
也不重新允许没有 RHS 的定义。`add_i64` 则展示检查加法的真实代价：无法静态证明安全的
固定宽度整数加法会带有 `overflow` 完成事实，调用者必须按已经批准的 `?|` 规则精确
结算或传播。两个已经具体但不同型的操作数仍直接报类型错误，而不会寻找共同类型。

已经冻结且本次不重问：普通 `T` 不含缺值；类型方案不读未来调用点；每个调用独立
实例化；未解类型不进入 SGIR/LLVM；公开、递归、原生/FFI 和类型化协议边界仍显式；
作者可写泛型、用户运算符实例与开放重载仍在 `F02` 门后。

### 11.3 其他语言哪些经验值得借，哪些坑不能复制

1. **C 的整型提升与 usual arithmetic conversions。** 小整数会先提升，混合宽度或
   符号性再按一组不直观规则转换；有符号溢出又不是普通可恢复结果。这样虽然方便旧
   硬件和 ABI，却使表达式类型与边界值难以从源码直接看出。Styio 不应复制“两个具体
   数值类型自动找共同类型”或把溢出留给优化器。参考
   [ISO C N1570](https://www.open-std.org/jtc1/sc22/wg14/www/docs/n1570.pdf) 与
   [WG14 safe arithmetic proposal N2428](https://www.open-std.org/jtc1/sc22/wg14/www/docs/n2428.pdf)。
2. **Rust 的上下文字面量与晚默认。** 无后缀整数先由上下文约束，仍欠约束时才默认
   `i32`；原始数值转换通常要求显式 cast。这证明“精确项先于存储类型”可用。但 Rust
   的 `Add<Rhs>` 具有开放 impl 与独立 `Output`，若照搬会立刻把 Q05 变成 trait
   coherence、搜索和歧义问题；debug/release 溢出差异也不应成为语言合同。参考
   [Rust literal expressions](https://doc.rust-lang.org/reference/expressions/literal-expr.html)、
   [`std::ops::Add`](https://doc.rust-lang.org/std/ops/trait.Add.html) 与
   [Rust coercions](https://doc.rust-lang.org/reference/type-coercions.html)。
3. **Haskell 的多态数值字面量。** `Num a => a` 能让定义保留 principal constraint，
   正好说明不必在 `x + 5` 处先猜具体类型；但开放 type class、歧义检查、defaulting
   与 monomorphism restriction 也说明“以后总能靠约束求解”会形成一整套隐藏规则。
   Styio 只需要封闭有限关系，不需要作者实例和开放字典。参考
   [Haskell numeric literals](https://www.haskell.org/onlinereport/basic.html#sect6.4.1) 与
   [ambiguity/defaulting](https://www.haskell.org/onlinereport/decls.html#sect4.3.4)。
4. **Swift 的无限精度解析与默认类型。** 编译器先用足够精度理解源码数字，再由上下文
   选类型；无上下文时默认整数/浮点类型。这值得借鉴，但默认类型本身必须是公开、稳定
   的语言语义，不能由平台、优化级别或后端决定。参考
   [Swift lexical structure](https://docs.swift.org/swift-book/ReferenceManual/LexicalStructure.html) 与
   [Swift basic types](https://docs.swift.org/swift-book/documentation/the-swift-programming-language/thebasics/)。

历史结论不是“所有语言都应默认同一宽度”，而是三条边界：不要过早定型、不要静默
提升两个已经具体的类型、不要用开放重载和后端行为填补规范空白。

### 11.4 方案比较与批准结果

#### 方案 A — 精确项 + 封闭标量关系 + 强制具体边界晚默认（已批准）

所有者于 2026-07-20 批准该整包；以下 10 条相互依赖的规则均为稳定子决策：

1. **字面量先保持精确。** 正/负整数保留精确有符号值；十进制保留精确十进制值。
   进制和分隔符只影响源码表示，不改变数学值。定义点泛化期间永不默认宽度。
2. **物化规则显式且失败关闭。** 整数字面量可物化为能完整容纳它的任一有符号整数；
   只有目标浮点格式能精确表示该整数时才可进入浮点上下文，避免静默丢失整数位。
   十进制字面量不隐式物化为整数；进入 `f32`/`f64` 时采用 IEEE round-to-nearest,
   ties-to-even。有限十进制源码值若大到只能成为无穷则在物化点报错。显式写出的
   `-0.0` 物化为 IEEE 负零，而整数 `-0` 与 `0` 是同一精确整数值。
3. **内建 `Add` 是编译器拥有的有限标量表。** 表只覆盖 `i8`、`i16`、`i32`、
   `i64`、`i128`、`f32`、`f64` 及可物化到这些类型的精确字面量；`bool`、`char`、
   `string`、容器和矩阵不因为当前实现碰巧接受 `+` 就自动进入本表。
4. **不做 C 式共同类型提升。** 两个已经具体的数值操作数只有同型时才直接相加；
   `i32 + i64`、`i64 + f64`、`f32 + f64` 都要求作者先使用日后批准的显式转换表面。
   一侧仍是精确字面量时，可先按另一侧具体类型物化；左右位置规则对称。
5. **结果类型由被选中的标量行唯一决定。** `T + T`、`T + Literal(v)` 与
   `Literal(v) + T` 都产生 `T`。两个仍为精确项的字面量可以先精确常量折叠；若结果
   到达必须拥有具体类型的普通值边界仍无上下文，再适用第 6 条。
6. **默认只发生一次且很晚。** 在普通绑定存储、非泛型返回或其他必须产生具体值的
   边界仍欠约束时，整数字面量默认 `i64`，十进制字面量默认 `f64`。默认不得发生在
   可泛化 callable 的方案内部，不得反向固定参数，也不得随平台或后端变化；超出默认
   类型范围时要求显式更宽类型，不按字面量大小悄悄改选 `i128`。
7. **算术结果与完成事实同表。** 有符号整数 `Add` 使用检查算术；上溢和下溢产生
   prelude 唯一的、无 payload 的名义完成族 `overflow`，不回绕、不触发未定义行为、
   不依赖 debug/release。它是普通完成族标识符而非关键词；`overflow => recovery`
   合法，`overflow(binding)` 因该族没有 payload 而报错。浮点 `Add` 固定采用 IEEE 754
   round-to-nearest, ties-to-even 和渐进下溢，保留 subnormal 与 signed zero，不读取宿主
   浮点舍入环境，也不允许 fast-math、FTZ/DAZ 或重结合改变语言结果。结果可以是无穷
   或 NaN，不产生 `overflow` 完成；NaN payload/canonicalization、相等与排序另留后续
   Q05 包，但优化器不得据此假设 NaN 或无穷不存在。
8. **编译期与运行时共用一份关系。** 常量折叠不能得到运行时同型运算不可能得到的值，
   也不能吞掉整数 `overflow`。诊断必须区分“字面量不能物化”“具体操作数类型不匹配”
   和“运行/常量运算溢出”；当前后端的 i64 默认、隐式字符串化或运算分支均非规范证据。
9. **泛化方案采用有限保守完成上界。** 若一个封闭 `Add` 约束的不同合法标量行具有
   不同完成集合，方案上界取这些行的有限并集。因此 `add_five` 的稳定推断方案带有
   `{overflow}`：即使某次调用最终实例化为 `f64`，当前阶段的调用者仍按这份可见上界
   结算或传播。这样支持用户要求的桥接型泛化，同时不偷偷引入依赖类型实参而变化的
   completion row；将来若要让具体实例缩窄调用义务，必须由 `F02` 单独准入。
10. **常量已知的溢出仍是同一个完成。** `127 + 1` 若在 `i8` 期望上下文中于编译期
    已知必溢出，常量求值器产生 `overflow` 控制边，而不是静默回绕，也不因“编译期已知”
    就另造一条无条件语法错误规则。若外围既未结算又不能按合同传播，才由现有静态完成
    检查报错；`small : i8 = 128` 这种单个字面量不能物化则始终是另一类静态类型错误。

方案 A 保留常用 `count := 1` 的简洁性，同时保证 `add_five` 不被该默认污染；封闭表使
类型求解、完成集合和代码实例均有限可枚举。

#### 方案 B — 精确项 + 封闭关系，但永不提供无上下文默认

除删除方案 A 第 6 条外，其余相同。它最严格，任何 `count := 1` 都必须从标注或调用
上下文获得具体类型，能彻底消除默认惊讶；代价是大量普通局部常量也需要类型标注，且
无助于表达能力。若所有者认为“任何隐式宽度都是不可接受的”，这是首选替代方案。

#### 方案 C — 字面量一出现就固定为 `i64` / `f64`

实现简单，却会让 `x + 5` 在定义阶段被无理由收窄为与 `i64` 相加，破坏已经批准的
Q02-INF 主方案，也使 `f32 + 5` 等自然上下文需要额外转换。拒绝。

#### 方案 D — C 式数值提升或开放 `Add` 实例搜索

前者把结果类型交给隐式共同类型规则，后者把一个有限内建表扩张为用户实例、优先级、
coherence、歧义与运行时字典问题。两者都显著扩大当前决策面；开放实例只可在 `F02`
重新准入，C 式提升不推荐。

## 13. 当前讨论包：Q04-Core — 静态所有权、捕获与能力图

### 13.1 用途与本次边界

Q04-Core 要让编译器在生成代码前唯一回答：一个值是在复制语义值、转移唯一 owner，
还是建立短期 borrow/view；闭包或 task 捕获后能否逃逸；endpoint 接收 copy、borrow
还是 consume；哪个作用域负责 drop/close。它用于防止悬垂 view、重复释放、隐式深拷贝、
资源别名竞争和捕获后生命周期不明，同时保留无 GC、无 ARC、无动态借用检查的 Thin
Artifact 路线。

本包只增加 Sema/HIR 内部事实和依赖边，**不增加任何 token、关键字、类型修饰符或
capture list 语法**。现有 `:=`、`=`、`->`、闭包/task、资源 session 和资源专属 `<<`
表面保持原义；表示层可以优化，但不能反向决定语言语义。

### 13.2 已冻结局部锚点不等于全局所有权模型

| 已有决定 | 已冻结内容 | Q04-Core 仍须补足 |
|---|---|---|
| Q01-A operation/completion | 一个 success type 加有限 nominal completion set；成功 transfer 为 Unit | copy/borrow/consume 的所有权 post-state，不扩充 OperationSummary |
| Q02-INF principal inference | 只有已证明 capture-safe 的 final、非递归、非边界 callable 才可泛化 | capture-safe 的可执行证明规则 |
| Q03-F evaluation/order | 严格值、依赖图、显式 effect/completion 序列、失败关闭与发布屏障 | ownership/alias/capability/drop facts 和边，作为 EvaluationFacts 输入 |
| 资源 session | body 仅 handles/anchors；session owner 不逃逸；owned child 在退出前 join；默认逆获取 Close | 这些局部规则如何映射到通用 owner/borrow/capture/drop 事实 |
| Block 退出 | last-borrow、child-join、commit、drop 等真实依赖优先；独立义务稳定逆登记 | 每个普通 owner 何时创建、转交或解除其 drop obligation |

因此，资源 session 已经是一个受限的仿射作用域实例，却没有自动批准“所有普通值、
聚合、闭包、task 和 endpoint 都使用同一全局规则”。Q04-Core 的任务是建立统一静态事实
接口，并把已经冻结的资源/session 行为作为必须满足的锚点，而不是重新解释它们。

依赖方向是单向的：Q04-Core 消费 Q01/Q02/Q03 的冻结合同；Q02 只消费 Q04 给出的
`capture_safe` 结论，Q03 只消费 Q04 给出的 EvaluationFacts/DAG 边。Q04 不改写 Q02 的
泛化边界，也不改写 Q03-F 的求值或发布语义。

### 13.3 其它语言的成功与失败经验

| 语言/路线 | 成功经验 | 不应复制的失败或代价 |
|---|---|---|
| C++ | RAII 能把资源释放绑定到词法退出；move 能表达所有权转交 | copy/move overload、隐式复制、引用悬垂和对象生命周期规则互相叠加；small-object 优化是表示技巧，不应成为语义分类 |
| Rust | affine owner、静态 borrow、作用域线程和 `Send`/`Sync` 证明了无 GC 也能安全转交 | closure 的 `Fn/FnMut/FnOnce`、显式 lifetime 与复杂诊断暴露较高作者负担；Styio 应保留内部事实，不照搬整套表面语法 |
| Swift | value semantics 配合 COW 证明“语义复制”不等于每次物理 memcpy；exclusive access 能保护原地更新 | ARC、逃逸闭包和运行时 exclusivity 不是 Thin Artifact 可依赖的兜底 |
| Clean / Cogent | uniqueness/linear typing 能在纯或函数式模型里安全做 destructive update，并可直接降低到原生表示 | 过度线性会把一次性资源纪律扩散到所有普通值；Styio 只让有身份 owner 仿射 |
| Go | escape analysis 可作为栈/堆优化，说明实现位置不应改变源码含义 | closure 捕获变量别名并依赖 GC；“编译器认为很小或未逃逸”不能充当语言 ownership 合同 |
| Pony/reference-capability 路线 | capability 能把别名和并发权限统一检查 | 大型公开 capability 格与 viewpoint adaptation 学习成本高；v1 应使用封闭内部事实，不引入用户可写能力代数 |

综合经验是：**从 Rust/Clean/Cogent 借静态唯一性，从 Swift 借语义与表示分离，从 RAII
借退出义务；拒绝 C++ 式隐式复制、Go/ARC 式运行时兜底以及把完整 capability 格暴露成
新语法。**

### 13.4 方案比较与推荐

| 方案 | 模型 | 结论 |
|---|---|---|
| **C：编译器推导的 value + affine owner + lexical borrow + endpoint protocol** | 由类型身份、使用、escape 和 endpoint 合同产生唯一事实；无新增语法 | **推荐**。可静态降低、与函数式值语义和现有资源锚点相容 |
| R：新增 `copy/move/borrow` 与 capture list | 作者逐点声明模式 | 暂拒；语法负担大，且不能替代 alias、escape、drop 验证 |
| S：按字节数或 “small” 阈值自动复制 | 表示大小决定 copy/move | 拒绝；ABI、优化级别或后端变化会改变程序含义 |
| I：遇到歧义时隐式 clone、ARC 或运行时 borrow check | 运行时弥补静态未知 | 拒绝；隐藏成本并破坏 Thin Artifact 与失败关闭 |

推荐方案 C 的判断顺序是：**语义类型与身份 → 使用/escape → endpoint 协议 → 唯一
capture/transfer 模式 → ownership post-state 与 DAG 边**。对象尺寸、寄存器数量、当前
ABI、逃逸优化结果和“复制看起来便宜”从不参与语义选择。

### 13.5 方案 C 的完整政策

1. **三类语义事实。** value-semantic 类型的复制产生不可通过身份观察区分的值；owner
   类型代表有唯一释放责任的身份并遵守仿射使用；borrow/view 是指向既有 place/region
   的非 owner 访问。`Unknown` 不能被猜成其中任一安全模式，相关操作失败关闭。
2. **语义与表示分离。** value copy 可以降低为寄存器复制、memcpy、COW、共享不可变表示
   或完全消除，只要身份与 mutation 不可观察。owner 即使只有一个机器字也不隐式复制；
   巨大不可变值即使采用共享表示仍是 value semantics。对象是否 “small” 永不决定复制。
3. **聚合传播。** 只有所有存储成员都具 value semantics 的 product 才自动 value-copyable；
   含 owner 成员的 product 整体仿射，整值 move 转交其中 owner。borrow/view 成员把其
   region/escape 约束传播到聚合。字段析构、部分 move 与 pattern 细节转 Q07，容器元素和
   迭代细节转 Q08。
4. **绑定可变性正交。** final `:=` 与 mutable `=` 只决定名字能否 rebind，不决定其 occupant
   是 value 还是 owner；final owner 仍可被 consume，mutable value 仍按值语义复制。任何
   binding 都不得通过语法类别暗中获得 clone 能力。
5. **rebind 与 consume 提交点。** 不消费旧 occupant 的 RHS 先按 Q03-F 完整求值；RHS 在
   commit 前 completion 时旧绑定保持原状态。RHS 正常后，rebind commit 原子安装新
   occupant，并完成 RHS source 所需的 move/consume；旧 owner 作为独立退出义务在最后
   borrow 之后再 drop。若旧 drop/close 产生 completion，新 occupant 仍保持已安装，
   completion 向外传播并停止后续 Block 项目；不回滚新值，也不暴露未初始化 slot。若 RHS
   本身 consume 旧 binding，则该 binding 在 consume edge 后立即 moved/unavailable；后续
   completion 同样不回滚 consume，recovery 也不复活旧 owner。
6. **词法 borrow/view。** borrow 具有编译期 region；shared read 可共存，exclusive mutation/
   consume 与任何重叠 borrow 冲突。borrow/view 不能返回到更长 region、存入更长寿容器、
   被未证明 join 的 task 捕获，或交给可能保留它的 endpoint。所有 borrow 必须在 owner
   drop、consume 或 rebind 前结束。
7. **capture 唯一推导。** capture mode 不是猜测或重载搜索：不可变 value-semantic 捕获是
   semantic snapshot-copy；只读且 non-escaping 的 owner 使用形成 shared borrow；需要
   mutation 的 non-escaping 使用形成 exclusive borrow；escaping closure/task 若需要
   owner，只能在协议允许时 consume。用途、escape 或 capability 不能给出唯一模式时静态
   报错，不插入 clone，也不新增 capture annotation。
8. **Q02 capture-safe 窄门。** 对 Q02-INF 的自动 rank-1 泛化，只有无捕获或只捕获不可变
   value-semantic snapshot 的 callable 才标记 `capture_safe=true`。捕获 owner、borrow/
   view、resource、task、mutable binding 或 Unknown 一律不满足该门；这只限制自动泛化，
   不把所有此类闭包宣布为非法。
9. **task capture。** structured task 对 value 采用 snapshot-copy，对 owner 采用显式
   推导出的 consume；borrow 仅在静态 join 边证明 task 先于 owner/drop 结束且 access
   不冲突时成立。资源 session 已冻结的 owned-child join 是该证明的一个实例；detached
   escape 不由 Q04 激活。
10. **endpoint 协议决定 transfer。** 每个静态 endpoint 协议行对输入声明唯一内部模式
    `copy`、`borrow` 或 `consume`，并为 normal 与每个 completion 出口给出 source/endpoint
    ownership post-state。`->` 只表达数据方向，既不按源对象大小选择模式，也不自己发明
    mode。没有适配行、缺少出口 post-state 或同时得到多个模式都失败关闭；value copy
    不等于资源 `<<` deep clone。
11. **consume 的精确 post-state。** source value 与 endpoint capability 仍按 Q03-F 作为
    独立前提准备。`consume` 只在 transfer 的 ownership-commit edge 使源 place
    moved/unavailable；commit 前 completion 保留 source，commit 后 completion 不复活
    source，释放责任已转给 endpoint/protocol。不同分支在 join 点必须给出兼容的 ownership
    post-state，否则静态拒绝。`borrow` 必须保证 endpoint 不保留 view，borrow 在 transfer
    settlement 后结束。
12. **封闭能力与 drop。** v1 的 copy/borrow/consume、read/write、clone、close 等能力是
    编译器/prelude/已批准资源协议的封闭事实，不是结构 duck typing 或用户可写 capability
    algebra。每个未转交的 owner 恰好贡献一个 drop/close obligation；consume 转移该义务，
    不复制它。
13. **退出依赖图。** drop/close 位于最后 borrow、相关 owned-child join 和必要 commit
    之后；资源族已冻结的 flush/close 依赖继续有效。无真实依赖的义务采用稳定逆登记序，
    不按指针、hash 或调度完成顺序。fallible drop/close 使用既有 operation/completion
    合同，不产生 ambient exception channel。
14. **独立 EvaluationFacts。** Sema/HIR 形成 `OwnershipKind`、`Place/Region`、`AliasAccess`、
    `EscapeClass`、`CaptureMode`、`EndpointMode`、`OwnershipPostState`、`CapabilityState`
    和 `DropObligation` 等内部事实，并向 Q03-F DAG 提交 borrow-conflict、consume、
    last-borrow、join、drop/close 与 transfer-commit 边。它们进入
    `EvaluationFacts`，**绝不添加到或改写**
    `OperationSummary(success_type, completion_set)`；Verifier、lowering 与 optimizer
    消费同一事实源。
15. **无新增语法且失败关闭。** 方案 C 不准入 public ownership modifier、lifetime、
    capture list、capability constraint 或隐式 clone。诊断必须指出 source place、所需
    mode、冲突 borrow/escape 与修复边界；信息不足时拒绝，而不是依赖后端顺序、GC、ARC
    或运行时借用表。

### 13.6 直接后果

- 普通标量与不可变 product 保持自然值语义；编译器可自由选择高效表示，作者不需要知道
  “复制了多少字节”。
- 资源、可观察身份对象和含 owner 的聚合不会被函数调用、捕获或 `->` 悄悄复制；每次
  owner 转交都有唯一 consume edge 和静态 post-state。
- non-escaping view 可以零拷贝，但无法越过 owner 生命周期；可变别名、task capture 和
  endpoint retention 在编译期合流为同一 alias/region 检查。
- Q02-INF 获得可执行且保守的 capture-safe 门；Q03-F 获得缺失的 ownership/drop 边，
  同时两者的既有公共摘要保持稳定。
- rebind 在 RHS 正常后先安装新 occupant，再结算旧 owner；因此旧 drop/close 即使产生
  completion，也没有隐式未初始化窗口或无法证明的“恢复旧值”，新 occupant 保持已安装。
- 代价是部分今天“碰巧能跑”的隐式 alias、Unknown/native capture 和多模式 endpoint 会
  变为诊断；这是失败关闭，不是兼容模式。完整迁移时旧 heuristics 必须删除，不能保留
  “按大小复制”或后端临时兜底。
